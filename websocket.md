#  Протокол WebSocket API

Документация по событийно-ориентированному взаимодействию в реальном времени (мессенджер, статусы, уведомления).

## 1. Подключение

**URL:** `ws://<host>/v1/ws`
**Протокол:** JSON
**Авторизация:** Стандартный JWT в заголовке `Authorization`.

```http
Authorization: Bearer <your_jwt_token>
```

---

## 2. Формат сообщения (Envelope)

Все пакеты данных (и входящие, и исходящие) упакованы в стандартный «конверт».

```json
{
  "type": "string",       // Тип события (action)
  "request_id": "string", // (Опционально) Клиентский ID для сопоставления ответа
  "payload": { ... }      // Объект с данными события
}
```

---

## 3. События: Клиент → Сервер (Исходящие)

### 3.1. `newMessage`
Отправка текстового сообщения.

**Payload:**
- `chat_id` (int64): ID чата.
- `content` (string): Текст сообщения. Может быть пустым, если есть `file_id`.
- `reply_to_message_id` (int64, опционально): ID сообщения, на которое отвечаем.
- `file_id` (string/uuid, опционально): ID заранее загруженного файла (`POST /v1/files/upload`). В ответном сообщении придёт объект `attachment` с публичным `url`.

> **`attachment`** в ответе несёт `url`, `file_name`, `mime_type`, `size`, а также — когда сервер смог их извлечь — `duration_ms` (аудио/видео) и `width`/`height` (изображения/видео). Поля опциональны (`omitempty`): для голосового придёт `duration_ms`, для фото — `width`/`height`. По ним клиент рисует placeholder до скачивания. MIME определяется по реальным байтам: голосовое `.m4a` отдаётся как `audio/mp4` (а не `video/mp4`).

**Пример:**
```json
{
  "type": "newMessage",
  "request_id": "c7b3-4f9a",
  "payload": {
    "chat_id": 42,
    "content": "Привет, во сколько встречаемся?",
    "reply_to_message_id": 1040
  }
}
```

> **Редактирование и удаление** сообщений выполняются по REST (`PATCH`/`DELETE`
> `/v1/chats/{id}/messages/{messageId}`), а не по WebSocket. Сервер сам разошлёт
> участникам события `messageEdited` / `messageDeleted` (см. ниже).

### 3.2. `messagesRead`
Уведомление сервера о прочтении сообщений в чате.

**Payload:**
- `chat_id` (int64): ID чата.
- `last_read_message_id` (int64): ID последнего просмотренного сообщения.

```json
{
  "type": "messagesRead",
  "payload": {
    "chat_id": 42,
    "last_read_message_id": 1050
  }
}
```

### 3.3. `userTyping`
Индикация набора текста. Рекомендуется отправлять не чаще одного раза в 3-5 секунд.

**Payload:**
- `chat_id` (int64): ID чата.

## 4. События: Сервер → Клиент (Входящие)

### 4.1. `newMessage`
Рассылка нового сообщения всем участникам (включая автора).

**Payload:** Полный объект сообщения.
- Может содержать `reply_to` — компактное превью цитируемого сообщения (`id`, `sender_id`, `sender_display_name`, `content`, `is_deleted`).

### 4.1.1. `messageEdited`
Сообщение отредактировано автором. Обновите его в списке по `id`.

**Payload:** Полный объект сообщения (как `newMessage`), с непустым `edited_at`.

### 4.1.2. `messageDeleted`
Сообщение удалено автором (мягкое удаление). Покажите плейсхолдер «сообщение удалено».

**Payload:**
- `chat_id` (int64)
- `message_id` (int64)
- Содержит `id`, `created_at` и вложенный объект `sender`.
- Если сообщение отправлено вами, `request_id` будет идентичен присланному вами ранее.

### 4.2. `messagesRead`
Приходит, когда кто-то из участников чата прочитал сообщения.

**Payload:**
- `chat_id` (int64)
- `last_read_message_id` (int64)

### 4.3. `userTyping`
Приходит, когда другой пользователь начал набирать текст.

**Payload:**
- `chat_id` (int64)
- `user_id` (int64): ID того, кто печатает.
- `display_name` (string): отображаемое имя того, кто печатает.

### 4.4. `error`
Ответ на некорректные действия или ошибки сервера.

**Payload:**
- `message` (string): Текст ошибки.

### 4.5. `presenceSnapshot`
Приходит **один раз сразу после подключения**. Текущий онлайн-статус всех, с кем
вы состоите в общих чатах. Используйте для инициализации индикаторов «в сети».

**Payload:**
- `users` (array): список объектов `{ "user_id": int64, "online": bool, "display_name": string?, "last_seen": int64? }`.
  `display_name` — отображаемое имя пользователя (`display_name`, если задан, иначе `username`; можно рисовать сразу, без отдельного запроса);
  `last_seen` (unix-секунды) присутствует только для офлайн-пользователей с известным временем визита.

### 4.6. `userOnline`
Кто-то из ваших собеседников по чатам подключился (перешёл в онлайн).

**Payload:**
- `user_id` (int64)
- `online` (bool): всегда `true`.
- `display_name` (string): отображаемое имя подключившегося (`display_name`, если задан, иначе `username`).

### 4.7. `userOffline`
Собеседник по чатам отключился (закрыл последнее соединение со всех устройств).

**Payload:**
- `user_id` (int64)
- `online` (bool): всегда `false`.
- `display_name` (string): отображаемое имя (`display_name`, если задан, иначе `username`).
- `last_seen` (int64): unix-секунды момента ухода в офлайн.

## 💡 Рекомендации по реализации

1.  **Оптимистичный UI:** При отправке `newMessage` сразу отображайте сообщение со статусом «отправляется» (часики). При получении входящего события с тем же `request_id` — меняйте статус на «доставлено» и обновляйте локальный ID на серверный.
2.  **Устойчивость к разрывам:** Реализуйте автоматическое переподключение (reconnect) с экспоненциальной задержкой. **При реконнекте догружайте пропущенное по REST**: по каждому чату вызовите `GET /v1/chats/{id}/messages?cursor=<последний_известный_id>`, а список чатов и непрочитанные — `GET /v1/chats`. WS-доставка событий — at-most-once (источник правды — БД), поэтому события, пришедшие пока вы были офлайн, восстанавливаются именно из REST.
3.  **Обработка дублей:** Игнорируйте входящие события `newMessage`, если сообщение с таким ID уже присутствует в локальном списке (актуально при переключении между REST и WS).
4.  **Presence:** Инициализируйте статусы из `presenceSnapshot`, далее обновляйте по `userOnline`/`userOffline`. Текущий снимок участников конкретного чата всегда можно получить через `GET /v1/chats/{id}/presence`.
